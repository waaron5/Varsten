# Fail-open SDK — Phase 1 design freeze

Status: **locked for Phase 2**. This document fixes the contracts the fallback SDK
and the server depend on so Phase 2 (TypeScript + OpenAI + non-streaming) can be
built without re-litigating decisions. Anything not frozen here is explicitly
deferred and labeled as such.

North star: **Varsten saves money when healthy, but never takes down the
customer's AI feature when Varsten is unavailable.**

Scope of the SDK overall: TS first, OpenAI-compatible chat completions first,
non-streaming first, streaming second, other providers after. This freeze covers
the contracts; Phase 2 implements only the non-streaming slice but must not
violate anything here.

---

## 1. The origin contract (the keystone)

The SDK's entire fallback decision reduces to one question: **did this failure
originate inside Varsten, or did Varsten faithfully relay a provider outcome?**
The server answers it with one header on **every** proxy response.

### `X-Varsten-Origin`

Stamped on every response the proxy emits, success or error:

- `varsten` — the response was generated by Varsten itself and no provider call
  succeeded for it. Examples: circuit open, rate limited, budget block, no
  provider key configured, internal 5xx, malformed/unparseable, `varsten_upstream_error`
  (Varsten could not reach the provider).
- `provider` — the body is a faithfully relayed provider result, whether a 200 or
  a provider error (provider 400/401/429/5xx, content/safety block). Varsten did
  reach the provider and is passing back what it returned.

Rules the SDK relies on:

1. **Transport failure** (no HTTP response at all: DNS, connection refused,
   connect timeout, TLS error) → treat as `varsten` origin → fallback eligible.
2. **Response present** → read `X-Varsten-Origin`.
   - `varsten` + failure status → fallback eligible.
   - `provider` → **never** fallback. Return the response (success or error) verbatim.
3. **5xx with the header missing** (old build, proxy crashed mid-response) →
   treat as `varsten` origin → fallback eligible. A header-less 5xx means Varsten
   itself is misbehaving; failing safe toward fallback is correct.

Without this header a provider 500 and a Varsten 500 are indistinguishable, and
the SDK would either under-fallback (lose uptime) or over-fallback (double-bill).
This header is non-negotiable and ships in Phase 2 before/with the SDK.

## 2. Error response schema

Extends the proxy's existing `{ "error": { "message", "type" } }` shape (it
already emits `varsten_circuit_open`, `varsten_rate_limited`,
`varsten_budget_exceeded`, `varsten_upstream_error`). Frozen additions:

```json
{
  "error": {
    "message": "human-readable, may change",
    "type": "varsten_circuit_open",
    "code": "circuit_open",
    "origin": "varsten"
  }
}
```

- `origin`: `"varsten" | "provider"` — mirrors the header, in the body, so SDKs
  that only see the parsed body still get it. Header is authoritative when both present.
- `code`: stable, machine-readable, decoupled from `message`. The SDK switches on
  `code`, never on `message`. Frozen v1 codes:

| `code` | HTTP | `origin` | Fallback? |
|---|---|---|---|
| `circuit_open` | 503 | varsten | yes |
| `rate_limited` | 429 | varsten | yes |
| `budget_exceeded` | 402 | varsten | **no** (see note) |
| `upstream_unreachable` | 502 | varsten | yes (default on) |
| `no_provider_key` | 502 | varsten | yes |
| `internal_error` | 5xx | varsten | yes |
| `bad_request` | 400 | varsten | **no** (client's malformed request) |
| `unauthorized` | 401 | varsten | **no** (bad `vk_` key — surface it) |
| (relayed) | any | provider | **no** |

Note on `budget_exceeded` (402): this is a **deliberate** customer-configured hard
cap. Falling back direct would defeat the cap the customer set. Default: **do not
fall back**; surface the 402. Revisit only if a customer explicitly wants caps to
be advisory. This is the one `varsten`-origin failure that intentionally does not
trigger fallback.

`origin` and `code` are a **versioned contract**. Changes are additive; existing
codes never change meaning.

## 3. Fallback policy (frozen)

"Fallback" = the SDK reissues the **original, unmodified** request to the customer's
provider directly, using the customer's local provider key.

### Fall back (Varsten-origin, no provider output produced or billed)

| Trigger | Why safe |
|---|---|
| DNS failure to Varsten | No upstream call happened |
| Connection refused / TLS error | Same |
| TCP connect timeout | Varsten never accepted the request |
| 5xx with `origin: varsten` (or header missing) | Varsten's own failure |
| `circuit_open` (503) | Provider may be fine; Varsten chose to fail fast |
| `rate_limited` (429) | Varsten's limit must never block customer prod |
| `upstream_unreachable` (502) | No output produced; direct retry is safe and may succeed via a different network path. The one "soft" case — if the provider is genuinely down the direct call also fails, costing one extra round trip, no double-bill. Default on. |
| `no_provider_key` (502) | Varsten cannot serve; direct path can |
| Malformed/unparseable Varsten response with no `origin: provider` | Treat as Varsten failure |

### Do NOT fall back

| Trigger | Why | Customer sees |
|---|---|---|
| Any response with `origin: provider` (200 or error) | Faithfully relayed; retrying direct double-bills / hits same sick provider | The provider's result/error |
| `budget_exceeded` (402) | Deliberate customer cap | The 402 |
| `bad_request` / `unauthorized` (Varsten-origin 400/401) | Client's own mistake | The error |
| Invalid customer request | Not a Varsten fault | Validation error |
| `≥1 token already streamed` | Cannot restart without garbling/duplicating | Terminal stream error |
| Read timeout after connection established (default) | Usually slow generation, not Varsten; aborting double-bills | Timeout error (opt-in override available) |

### Distinguishing Varsten-origin from provider-origin

Exactly the §1 rules: transport failure → varsten; else read `X-Varsten-Origin`;
header-less 5xx → varsten. Never infer origin from status code alone.

## 4. Timeout / retry / circuit breaker policy (frozen defaults)

Defaults chosen to make fallback safe (no double-bill) first, fast second.

| Setting | Default | Rationale |
|---|---|---|
| Varsten connect timeout | **1s** | Healthy Varsten accepts instantly; 1s without a connection = infra problem = fall back |
| Varsten total (non-streaming) | **= provider tolerance (e.g. 60s, matching `proxy_upstream_timeout_seconds`)** | Healthy Varsten adds ~1-5ms; a slow total is slow generation, not Varsten |
| Varsten first-byte (streaming) | **2-3s** | No first SSE chunk in window = stalled before output = safe to fall back |
| Provider-direct total | **= customer's normal provider timeout** | The direct path behaves like calling the provider directly |

**Read/total timeout does NOT trigger fallback by default.** A slow read means
Varsten accepted the connection and is presumably forwarding; aborting to retry
direct risks double-bill. Opt-in `fallbackOnReadTimeout: true` for customers who
explicitly prefer availability over the rare double-bill, documented with the tradeoff.

**Retries:** the SDK does **not** retry Varsten on the same request. One Varsten
attempt → success, single direct fallback attempt, or surfaced error. No N×retry
against Varsten (that builds retry storms). The direct attempt is single; the
provider SDK's own internal retries apply if the customer configured them.

**Local SDK circuit breaker** (anti-storm, per-process, per-Varsten-host):
- Track consecutive `varsten`-origin failures.
- After **K = 5** consecutive failures → **open**: skip Varsten, go direct for a
  cooldown (**30s**, jittered ±20%). During a real outage the customer pays the 1s
  connect timeout at most K times, not per request.
- After cooldown → **half-open**: route one request through Varsten. Success →
  close. Failure → reopen with backoff, capped at **5 min**.

**Double-billing defenses (in order):**
1. Timeout discipline — never fall back on read timeout by default (above).
2. **Idempotency key** — the SDK generates a UUID per logical request and sends
   `Idempotency-Key`. Server accepts and dedupes within a short window. This makes
   even a retried direct call safe. **Plumbing decision: land in Phase 2 if cheap,
   otherwise Phase 3.** The contract (header name `Idempotency-Key`, SDK-generated
   UUID) is frozen now so both sides agree.
3. `fallbackOnReadTimeout` is opt-in only.

**Partial outages:** per-request decisions plus the breaker. A flapping Varsten
falls back per failed call until K consecutive failures open the breaker into full
bypass; half-open probing restores the optimized path. No storm; every call served.

## 5. Streaming behavior (frozen; implemented in Phase 3)

The first-token boundary is the whole safety model.

- **Varsten fails before the first token** (connect error, first-byte timeout,
  immediate `varsten`-origin error frame): fallback is safe — nothing reached the
  customer. Reissue the stream through the direct provider.
- **Varsten fails after ≥1 token emitted:** **no fallback, ever.** Surface a
  terminal stream error event and end. The customer sees the tokens so far then an
  error — identical to the provider dropping mid-stream.
- **Never silently restart mid-stream.**
- A `hasEmitted` flag gates the fallback option; it flips the instant the first
  chunk is yielded to the caller.
- Observability distinguishes `fallback{phase: "pre-first-token"}` from
  `stream_failed{phase: "mid-stream", tokens_emitted: N}`. Mid-stream failure is a
  real (rare) customer-visible failure and must be visible, not hidden.

## 6. SDK API surface (frozen for TS)

**Packages:** `@varsten/openai` (public, first), `@varsten/core` (internal engine:
fallback decision, local breaker, error taxonomy, telemetry; reused by future
`@varsten/anthropic`, `@varsten/gemini`). `core` is **not** public in v1.

**Install:** `npm install @varsten/openai` (peer-depends on `openai`).

**Design principle:** a delegating wrapper around the official provider client, not
a reimplementation. Internally holds two stock `openai` clients — `primary`
(baseURL = Varsten, key = `vk_`) and `fallback` (provider default baseURL, key =
provider key). Exposes the surface the customer already uses.

**Env vars (frozen names):**

| Var | Purpose | Sent to |
|---|---|---|
| `VARSTEN_API_KEY` | the `vk_` key | Varsten only |
| `OPENAI_API_KEY` | provider key | provider only, on fallback |
| `VARSTEN_BASE_URL` | optional override (default `https://api.varsten.ai/v1`) | — |
| `VARSTEN_FALLBACK` | `auto` (default) \| `off` | — |

**Constructor + usage (frozen shape):**

```ts
import { VarstenOpenAI } from "@varsten/openai";

const client = new VarstenOpenAI({
  varstenApiKey: process.env.VARSTEN_API_KEY,
  openaiApiKey: process.env.OPENAI_API_KEY,   // never sent to Varsten
  fallback: "auto",                            // "auto" | "off"
  onFallback: (e) => logger.warn("varsten_fallback", e),
});

const res = await client.chat.completions.create({
  model: "gpt-4o-mini",
  messages: [{ role: "user", content: "hi" }],
});
```

**Config surface (frozen):**
- `varstenApiKey`, `openaiApiKey` (or read from env)
- `baseURL` override
- `fallback`: `"auto" | "off"` — global enable/disable
- `onFallback(event)`: synchronous, fast (customer's logger/metrics)
- `fallbackOnReadTimeout`: boolean, default `false`
- `timeouts`: `{ connectMs, varstenTotalMs, providerTotalMs }` overrides
- `fallbackModel?`: optional; **default is identity** — the direct call uses the
  original model and body with no Varsten routing applied.

**Observing fallback (three layers):**
1. `onFallback(event)` — immediate, in-process, always works (even when Varsten is
   fully down).
2. Response annotation — non-enumerable `res._varsten = { servedBy: "varsten" |
   "provider-fallback", reason }` (non-enumerable so it never breaks existing
   serialization).
3. Best-effort telemetry to Varsten (§7).

**`onFallback` event shape (frozen):**
```ts
type FallbackEvent = {
  requestId?: string;        // Varsten's X-Varsten-Request-Id if one was issued
  reasonCode: string;        // e.g. "connect_timeout", "circuit_open", "5xx"
  varstenStatus?: number;    // HTTP status, if a response arrived
  phase: "pre-request" | "pre-first-token" | "post-first-token";
  model: string;
  latencyMs: number;
  sdkVersion: string;
};
```

## 7. Telemetry model (frozen)

**Principle: telemetry must never block or slow the customer request.**

- **Local first:** every fallback fires `onFallback` synchronously and increments a
  local counter. Always works, even in a full Varsten outage.
- **Best-effort remote:** the SDK queues a marker and flushes **fire-and-forget,
  off the request path**, with a hard short timeout and a bounded in-memory buffer
  (drop oldest on overflow). A failed flush is silently dropped.
- **Endpoint:** `POST /v1/telemetry/fallback`, `vk_`-authed, write-only,
  rate-limited, validates against the allowlist below and **rejects anything that
  looks like content**.

**Safe field allowlist (frozen — nothing else may be sent):**
`request_id`, `timestamp`, `reason_code`, `phase`, `varsten_status`, `model`,
`latency_ms`, `sdk_version`. **Never** prompt text, completion text, messages, or
keys.

**Dashboard:** a "Fallback events" panel — count over time, reason breakdown,
affected projects, and an outage-window banner ("Varsten served 0 of N requests
14:02–14:09; M fell back to provider"). Turns an outage into a trust artifact.

**Missed savings:** estimate forgone savings during fallback windows as
`(fallback count) × (recent avg savings-per-request on that route)`, labeled
**estimated/forgone**, never realized. Consistent with "no painted-on savings."

**Coverage:** Proof/Analysis numbers during fallback windows are flagged "partial
coverage — N requests bypassed Varsten." Never silently undercount.

## 8. Required server-side changes (specified here, built in Phase 2)

Phase 1 freezes the contracts; Phase 2 implements. Frozen list:

1. **`X-Varsten-Origin` on every proxy response** (§1). The keystone.
2. **Error schema `origin` + stable `code`** (§2).
3. **In-process API-key cache** — cache `hash(vk_) → (project, api_key)` with TTL
   **30–60s**. On a DB error for a **cached/known** key, serve from cache instead
   of 500. **Unknown keys still hit the DB and fail closed; negative lookups are
   not cached** (or cached ≤2s) so a freshly created key isn't locked out. Documented
   tradeoff: revocation lag = TTL. Fixes the current hard DB dependency in
   `_api_key_context_async` that 500s the proxy on a DB blip.
4. **Circuit breaker stays.** Its 503 `circuit_open` is *good* with the SDK (fast
   fallback). Requirement: it must carry `X-Varsten-Origin: varsten`. (Optional,
   lower priority: a server config to fail-open-forward for base-URL-mode users who
   have no SDK.)
5. **Health endpoints:** `GET /v1/health` — cheap, **no DB**, 200 if process alive
   (SDK recovery probe + onboarding connection test). `GET /v1/health/deep` — checks
   DB + provider-key presence (onboarding readiness + monitoring), off the SDK hot path.
6. **Telemetry ingest:** `POST /v1/telemetry/fallback` (§7).
7. **Idempotency:** accept `Idempotency-Key` on `/v1/chat/completions`, dedupe in a
   short window (Phase 2 if cheap, else Phase 3).
8. **Logging:** log `origin`, `code`, and whether a request was breaker-short-circuited.
9. **Tests:** assert `X-Varsten-Origin` on every response branch (success,
   circuit-open, rate-limit, budget, no-key, upstream-error, provider-4xx,
   provider-5xx); auth-cache hit/miss/DB-down/unknown-key/revoked-key; health
   endpoints; telemetry content-rejection.

## 9. Acceptance criteria for the word "fail-open"

The product may use "fail-open" in production marketing only when **all** pass in
CI and a staged chaos run:

1. With a valid provider key and valid request, if Varsten is unreachable **before
   response output begins**, the SDK calls the provider directly and returns a valid
   response **with no customer code change** (non-streaming, and streaming-pre-first-token).
2. A provider-originated error (400/401/safety/5xx) is **never** converted into a
   duplicate direct call.
3. No fallback path produces duplicate billable output for a single logical request
   in the connection-failure and Varsten-origin-error cases.
4. Mid-stream Varsten failure never silently restarts; it surfaces a terminal error.
5. During a sustained outage, the SDK enters bypass after ≤K requests and stops
   paying per-request Varsten timeouts.
6. Telemetry failure never adds measurable latency to the AI request.
7. A Varsten DB outage does not return 500 to the caller for a known active key, and
   the SDK falls back cleanly if it does.
8. The onboarding fallback simulation passes end-to-end for a real project before it
   is marked "production fail-open ready."

Until all eight pass, the product says **"automatic provider fallback (beta)"**, not
"fail-open."

## 10. Explicitly deferred (not Phase 1, not frozen)

- Streaming implementation (frozen *behavior* in §5; built Phase 3).
- Anthropic / Gemini SDK packages (pattern reuses `@varsten/core`).
- Embeddings, batch, tool-call-specific handling beyond pass-through.
- Server-side provider-key passthrough so Varsten never stores the provider key
  (option "b") — later, when an enterprise review demands it. v1 keeps the existing
  server-side key vaulting and uses the local key purely as the fallback credential.
- Redis-backed shared circuit breaker, multi-region/HA, in-VPC/self-hosted.
- Onboarding two-path redesign and the full marketing rewrite (Phases 4–5).

---

## 11. Open questions to resolve before/within Phase 2

- **Idempotency timing:** Phase 2 or Phase 3? Affects how fully criterion 3 is met
  for the read-timeout window. Header/UUID contract is frozen regardless.
- **Prod topology** (single-instance vs multi-region) — changes outage probability,
  not the design; confirm before chaos runs.
- **DB pool exhaustion** under a provider slowdown could turn a slow provider into a
  Varsten-wide 5xx storm — which *fails open* with the SDK, but worth a soak test.
- **`upstream_unreachable` fallback default-on** — revisit if it causes wasted
  double attempts against a genuinely-down provider.

deferred item is deployed-image contract polish, not a gap in the safety claim.
